Partie de l'écosystème OpenDefender. Marché cible : France, Belgique, Maghreb, Afrique subsaharienne.

## Architecture obligatoire
Backend — Clean Architecture stricte :
  /cmd/server/main.go         → DI container, graceful shutdown
  /internal/domain/           → entités pures (pas de Fiber, pas de GORM ici)
  /internal/application/      → use cases (1 use case = 1 fichier)
  /internal/infrastructure/   → repositories, messaging, integrations
  /internal/api/http/         → handlers Fiber + middleware
  /pkg/                       → packages partagés (scoring, cti, notify, export, ai, crq)
 
Frontend — Feature-based :
  /src/features/[module]/     → pages, components, hooks, stores par feature
  /src/shared/                → design system, hooks globaux, utils
  /src/services/              → client API typé (généré depuis OpenAPI)
  /src/locales/               → fr.json, en.json

## Formule Score Engine
Score = Probability (0.0–1.0) × Impact (0.0–10.0) × AssetCriticality (0.1–3.0)
Criticality : score ≥ 7.0 = critical · ≥ 4.0 = high · ≥ 2.0 = medium · < 2.0 = low

## Smart Risk Calculation (spec §8 « Calcul de risque intelligent »)
Moteur **additionnel** au Score Engine classique (qui reste la source de vérité `Risk.Score`). Ne le remplace PAS.
- **Moteur pur** : `pkg/scoring/smart.go` (`ComputeSmart(SmartInput, FactorWeights) SmartResult`), stdlib, déterministe, testé. Le Score Engine `P×I×AC` (`engine.go`) est inchangé.
- **Formule** : `SmartScore = 100 × Σ (poids_normalisé_i × facteur_i)` sur **8 facteurs**, chacun normalisé dans `[0,1]` (1 = risque maximal). Bandes : ≥75 critical · ≥50 high · ≥25 medium · <25 low.
- **8 facteurs** (constantes `FactorKey`) et leur normalisation :
  1. `business_criticality` = `AssetCriticality.ScoreFactor()/3.0` (fallback impact/10×3 si pas d'actif) ;
  2. `internet_exposure` = tags risque (`internet-facing`→1.0, `internal`→0.1) sinon type d'actif ;
  3. `vulnerabilities` = `0.7×(maxCVSS/10) + 0.3×log-échelle(nb)` sur les vulns ouvertes de l'actif ;
  4. `control_maturity` = `1 − couverture_contrôles_implémentés` (neutre 0.5 si pas de compliance) ;
  5. `incident_history` = log-échelle du nb d'incidents passés de l'actif ;
  6. `exploitability` = max(EPSS, KEV→0.95, exploit→0.70, maturité) ;
  7. `financial_value` = `min(ALE_XAF / référence, 1)` (référence défaut 50 M FCFA, ALE via `pkg/crq`) ;
  8. `threat_intel` = signal CTI (KEV→1.0, sinon origine `cti_auto`/CVE→0.7).
- **Pondérations configurables par tenant** : `domain.RiskScoringWeights` (1 ligne/tenant, index unique `tenant_id`, 8 colonnes `numeric(6,4)`, défauts biz .15/expo .10/vuln .20/ctrl .10/incid .10/exploit .15/fin .10/cti .10). **Valeurs relatives** → `normaliseWeights` les ramène à somme 1.0 (clé absente = défaut, négatif = 0). `ToFactorWeights()`/`ApplyFactorWeights()` font le pont domaine↔moteur ; `Validate()` (chaque ∈ [0,1], au moins un > 0).
- **Persistance** : colonnes `smart_score`/`smart_level`/`smart_factors`(jsonb breakdown gelé)/`smart_computed_at` sur `risks` (migration `0035`, AutoMigrate `RiskScoringWeights` + colonnes). Write-back ciblé `GormRiskRepository.UpdateSmartScore` (pas de spam d'historique, comme `UpdateScore`).
- **Assemblage** : `application/risk/compute_smart_score.go` — `ComputeSmartScoreUseCase` (ports **optionnels** nil-safe via `With*` : assetRepo, vulnLister, compliance, incidents, quantifier, persister) ; `Execute(persist)` calcule+cache, `Preview(weights)` simule sans persister. Chaque source manquante dégrade son facteur, jamais d'échec.
- **Endpoints** : `GET /risks/:id/smart-score` (calcul+cache, `risks:read`), `POST /risks/:id/smart-score/simulate` (aperçu non-persisté, `risks:read`), `GET /risk-scoring/weights` (`risks:read`), `PUT /risk-scoring/weights` (**admin**). OpenAPI tag « Smart Risk Calculation ».
- **Frontend** : `features/risks/SmartRiskRadar.tsx` (radar Recharts + breakdown classé), onglet « Score intelligent » du drawer (`RiskRegisterPage`), écran `RiskWeightsSettings` (`/risks/weighting`, sliders + part effective normalisée, garde admin). Service/hooks typés `smartScoreService.ts`/`useSmartScore.ts`.

Il **saute** les mutations sans `tenant_id` (jamais de fuite cross-tenant) et la table `audit_events` elle-même. **L'acteur (« Qui »)** : un middleware monté sur le groupe `protected` (dans `main.go`) estampille `Actor{ID, TenantID, IP, UA}` sur `c.UserContext()` via `audittrail.WithActor` ; tout repo qui fait `db.WithContext(c.UserContext())` (asset, compliance…) propage l'acteur au plugin. **Limite honnête** : les `Updates(map[string]interface{})` (ex. update d'Asset) sont journalisés sans diff (le PK n'est pas dans le reflect map) → pour un diff garanti, utiliser le `Recorder` explicite. **`Recorder`** (`application/governance/audit_usecases.go`) = écriture explicite best-effort/nil-safe pour les actions à forte valeur (approbations, délégations, export) ; les use cases l'appellent. L'ancien `AdminAuditEvent` (jamais câblé) est **supplanté**.
- **Moteur d'approbation (structure)** : `application/governance/approval_usecases.go`. Un admin crée un `ApprovalWorkflow` liant `(entity_type, action)` (ex. `risk_acceptance`/`accept`) à une chaîne ordonnée d'étapes (chacune : `approver_role` éligible + `min_approvals`). `SubmitApprovalRequest` trouve le workflow (`FindWorkflow`), **snapshote ses étapes** sur la requête (les éditions ultérieures du workflow ne réécrivent pas les requêtes en vol) → `pending`, step 0. **`DecideApprovalStep` = le cœur du contrôle Maker-Checker** : impose (1) **four-eyes** — le demandeur (`RequestedBy`) ne peut jamais approuver sa propre requête ; (2) **éligibilité par rôle** par étape (un admin satisfait toute étape) ; (3) **pas de double-signature** d'une étape par le même approbateur ; (4) la **barrière min-approbations** avant d'avancer ; dernière étape → `approved`, tout `reject` → `rejected` (les deux résolvent). L'application effective de la décision approuvée reste au demandeur via le `payload` (prochaine itération : appliquer automatiquement).
- **Délégations** : `delegation_usecases.go` — Create (refuse auto-délégation / perms vides / `end<=start`), List (projection `expired` en lecture si la fenêtre a expiré), Revoke, `ResolveEffectivePermissions` (union des droits des délégations actives *maintenant* pour un utilisateur — ce qu'une couche d'autz OR-erait à ses permissions propres).
- **Vérifier les permissions dans le code (middlewares)** : les routes sont montées sous `protected := api.Use(middleware.Protected(...))`. Gardes disponibles : `middleware.RequirePermission("risks:read")` (match wildcard : `risks:*` couvre `risks:read`, `*` couvre tout — lit `c.Locals("permissions")`) ; `middleware.RequireRole("admin", "root")` (lit `c.Locals("org_roles")`). Dans un handler : `middleware.GetContext(c)` → `{UserID, OrganizationID}` (helpers partagés `tenantID(c)`/`userID(c)`), et `middleware.GetUserClaims(c)` → `*authpkg.Claims` (`HasPermission("*")`, `OrgRoles`). Les routes governance : audit-trail + config workflow = `RequireRole("admin","root")` ; délégations + décisions d'approbation = membre authentifié (les use cases imposent four-eyes/rôle en interne). **Piège Fiber** : les sous-chemins statiques (`/governance/audit-events/export`, `/governance/delegations/effective`) sont montés **avant** les routes `/:id`.
- **Endpoints** : `/governance/audit-events` (+`/export` CSV, admin), `/governance/delegations` (GET/POST, `/:id/revoke`, `/effective`), `/governance/workflows` (CRUD admin), `/governance/approvals` (GET inbox + POST submit, `/:id` + `/:id/decide` + `/:id/cancel`). **Frontend** `features/governance` : `GovernancePage` à 4 onglets (`/governance`, item sidebar « Gouvernance » groupe Admin, i18n `n_governance`) — journal d'audit interactif (**diff Avant→Après** coloré par champ + filtres + export CSV), boîte de réception d'approbation (chaîne d'étapes + approuver/rejeter/annuler), délégations (create/revoke), constructeur de workflow (add/remove étapes). ## RBAC — Rôles métiers GRC (Business Roles)
Système de **rôles métiers** par-dessus le RBAC runtime existant. **Additionnel** — le chemin d'autorisation effectif (login → `OrganizationMember.Role` → JWT `permissions` → `middleware.RequirePermission`) est conservé ; on donne enfin à un membre `user` un moyen cohérent d'obtenir les chaînes de permission que les routes vérifient. Branche `feature/rbac-business-roles`. Détail complet : `docs/RBAC_BUSINESS_ROLES.md`.
- **Constat d'audit** : seuls 3 rôles d'org existent (`root`/`admin`/`user`) ; `root`/`admin`→`["*"]`, mais un `user` ne recevait ses permissions que d'un `Profile` (vocabulaire étroit, jamais aligné sur `risks:create`, `compliance:frameworks:read`, `vulnerabilities:read`, `scanner:*`, `automation:*`, `reports:board:*`, `incidents:*`) → **un `user` était verrouillé hors de la majorité de l'app**. Le frontend n'injectait même pas `user.permissions` (elles vivent dans le JWT) → `usePermissions()` niait tout. Deux systèmes RBAC hérités (`domain/rbac.go`+`RoleService`, `RequirePermissions` pluriel) pilotent des écrans d'admin mais **pas** l'autorisation runtime.
- **Source de vérité pure** : `internal/domain/business_roles.go` (stdlib, testable) — `PermissionCatalog` (46 permissions = **exactement** les chaînes des gardes de route, libellés FR/EN + groupe) et **11 présets least-privilege** : `rssi`, `dsi`, `risk_manager`, `auditor`, `compliance_officer`, `internal_control`, `asset_owner`, `risk_owner`, `security_analyst`, `executive`, `viewer` — chacun → liste de permissions + `default_landing`. `ValidateBusinessRoles()` (test) garantit qu'aucun préset ne référence une permission hors catalogue. Le **Tenant Admin** = rôle d'org `admin` (`*`), pas un préset.
- **Résolution** : `OrganizationMember.BusinessRole` (colonne, migration `0038`, AutoMigrate) + `OrganizationMember.EffectivePermissions()` — **point unique** : root/admin→`["*"]`, sinon union(préset, règles `Profile`) dédupliquée. Utilisé au **login** (`application/auth/login.go`, renvoie `business_role`) **ET** au refresh (`SessionResolver` dans `main.go`) → un rôle métier survit au refresh.
- **API** : `GET /rbac/business-roles` (catalogue+présets, tout membre), `GET /rbac/members` (membres+accès résolu, admin), `PUT /rbac/members/:userId/business-role` (affecter/effacer un rôle métier + option changer le rôle org ; `root` protégé). Use cases `application/rbac` + `GormMemberRBACRepository` (tenant-scoped, Update scopé id+org). **Incidents** convertis de `RequireRole("admin","analyst")` (où « analyst » n'est pas un rôle runtime → admin-only de fait) vers `incidents:*`.

Scopé en garde par-route.

Zéro `any`.

## `<DataTable>` — la table unique de l'app + interdiction des boutons décoratifs

**Règle structurante (à faire respecter dans toute revue)** : aucun élément interactif ne peut être mergé sans **(a)** un handler réel, **(b)** un état loading/success/error **visible**, **(c)** un test E2E vérifiant l'**effet observable**. *Dans un outil de sécurité, un bouton qui ment est une vulnérabilité de confiance.*

- **Un seul composant** : `frontend/src/shared/datatable/` (`DataTable.tsx` + `types.ts` + `useTableState.ts` + `RowMenu.tsx` + `FilterPanel.tsx` + `ColumnsMenu.tsx` + `BulkBar.tsx` + `exportCsv.ts`). L'ancien `shared/DataTable.tsx` (tri client, sans virtualisation) est **supprimé**. La règle (a) est **rendue structurelle par les types** : une colonne n'est triable que si elle déclare *comment* trier (`sortKey` serveur / `sortValue` client), une facette que si elle déclare *comment* filtrer, une action de ligne que si elle a un `onSelect` — un en-tête décoratif est inexprimable.
- **Capacités** : virtualisation `@tanstack/react-virtual` (lignes espaceuses en `<tr>`, sémantique table intacte, seuil 30 lignes) · **tri + pagination serveur** · facettes réelles **dans l'URL** (`?q=&sort=score:desc&page=2&size=50&f.criticality=critical,high`) avec compteur de résultats, réinitialisation et **filtres sauvegardés nommés** (localStorage par `id` de table) · **recherche instantanée séparée des filtres** (deux affordances distinctes, débouncée 220 ms) · sélection **« page » vs « les N résultats »** (escalade explicite, jamais implicite ; toute modification de la vue purge la sélection) · **barre d'actions groupées flottante** gardée par permission, chaque action affichant son propre état · **menu de ligne en PORTAIL** (`@floating-ui/react`, flip + shift + size) · colonnes affichables/masquables/réordonnables **persistées par utilisateur** · **export CSV** de la sélection ou de la vue (colonnes visibles, dans l'ordre, échappement anti-injection de formule) · états skeleton/empty/no-results/error+retry · navigation clavier complète (↑↓, Home/End, PageUp/Down, Espace = sélection, Entrée = ouvrir, Échap = désélectionner) + `role=grid`/`aria-rowcount`/`aria-sort`/`aria-selected`.
- **Deux modes, documentés honnêtement** : `mode="server"` (risques, vulnérabilités, piste d'audit — l'API pagine et trie) et `mode="client"` (actifs, mitigations, incidents, jetons API — ces endpoints renvoient la collection entière **par nécessité** : l'Asset Universe a besoin de tous les nœuds, le Kanban/Gantt de toutes les mitigations). Détail : `docs/ui/dead-controls.md` §4.
- **7 registres migrés** dans l'ordre demandé : registre des risques (référence), vulnérabilités, actifs, mitigations (vue Table), incidents, piste d'audit (le diff Avant→Après passe d'un expander en ligne à un **drawer**), jetons API.
- **Backend (au-dessus du prédicat tenant, RÈGLE #2)** : `GET /risks` accepte désormais les facettes `criticality` / `phase` / `source` et `status` **multi-valeurs** (listes séparées par des virgules, `csvValues` → paramètres liés dans un `IN`), tri autorisé sur `name`/`criticality`/`source`, et la recherche `q` combine le `tsvector` **OR** un `ILIKE` — le `plainto_tsquery` seul est exact au lexème près : taper « log » ne remontait rien alors que « Log4Shell » était dans le registre.
- **Audit des boutons morts** : `docs/ui/dead-controls.md` recense **13 contrôles morts en production** (traités) + 4 dans du code inatteignable (fichiers supprimés) + 5 laissés avec leur raison. Notamment : point vert « Realtime » → **vrai indicateur de connexion** (`lib/connection.ts`, alimenté par les événements online/offline **et** l'issue de chaque appel axios ; un 4xx n'est pas une panne) · **micro supprimé** · « Voir toutes les notifications » **supprimé** (il ne faisait que fermer le panneau) · **« Supprimer l'organisation » implémenté** (c'était un `<button>` sans `onClick` — `DELETE /rbac/tenants/:id` + radiographie d'impact + logout) · Actualiser / Synchroniser / Matcher → états en vol visibles · funnel de l'Asset Universe → **vrai filtre par criticité** (masque aussi les arêtes pendantes).

## Activation & Onboarding — le parcours « inconnu → Aha en < 8 min »
**Cause racine corrigée** : l'état d'activation vivait **côté client** (localStorage + comptes dérivés dans le composant checklist). D'où toute la famille de bugs : checklist qui ne se coche pas (drapeau écrit sur un appareil, lu sur un autre), confettis aléatoires (l'heuristique « c'est fait ? » rejouée à chaque render), **deux items barrés après un seul import** (deux étapes client dérivées du même compteur). L'état est désormais **dérivé d'événements serveur**. Branche `feature/activation-onboarding-aha`.
- **Modèle** (`internal/domain/activation.go`, migration `0043` + AutoMigrate) : `ActivationEvent` (journal **append-only** : tenant, user, `event_key`, `occurred_at`, `payload` jsonb — la lecture ne prend QUE la **première occurrence par clé**, donc une étape terminée ne se dé-coche jamais et son `completed_at` ne bouge plus) ; `ActivationCelebration` (registre par utilisateur, unique `(user_id, step_key)` — c'est *ça* qui rend la célébration idempotente entre reloads et appareils) ; `OnboardingProgress` (état du wizard, **par utilisateur**, reprenable). **Catalogue d'étapes en code** (`activationSteps`) avec l'invariant clé : **1 étape ↔ 1 `event_key`**, imposé par `ValidateActivationSteps()` + test — un import ne peut donc plus cocher deux lignes.
- **Événements émis depuis le domaine** (port étroit `ActivationRecorder` déclaré par chaque use case, satisfait structurellement, `WithActivation(...)` **optionnel et nil-safe**, **sans retour d'erreur** : noter un jalon ne doit jamais faire échouer l'action métier) : `signup` (à l'inscription, ancre t0) · `profile.completed` · `risk.created` · `framework.imported` (**un seul par import**, quel que soit le nombre de contrôles) · `asset.connected` · `mitigation.created` · `member.invited` · `report.generated` · `aha.reached`.
- **Aha moment (spec §7)** = « premier score cyber calculé sur les données **propres** de l'utilisateur **AVEC** au moins un écart de conformité identifié » (`AhaSignal.IsAha()`). Détecté là où le score est calculé (`GetExecutiveDashboardUseCase`, via un port `AhaRecorder` primitif — zéro cycle d'import), enregistré **une seule fois par tenant**. **Métrique** : `openrisk_time_to_aha_seconds` (histogramme, buckets serrés autour du seuil) + `openrisk_activation_events_total{event_key}` + `openrisk_aha_reached_total`, dans `pkg/monitoring` (enregistrées **à l'import**, pas via un collector que personne ne construit). **`GET /metrics` sert enfin le format d'exposition Prometheus** (adaptor+promhttp, hors `/api/v1` et hors porte d'auth) — il renvoyait du JSON et n'était même pas monté. Alertes `SlowTimeToAha` (**P50 > 12 min**) + `NoActivationDespiteSignups` dans `deployment/monitoring/alerts.yml`.
- **Endpoints** : `GET /activation/state` (étapes + copie FR/EN + `completed_at` + `celebrate`), `POST /activation/celebrated`, `GET /onboarding/state`, `PUT /onboarding/steps/:step`, `POST /onboarding/complete`, `GET /onboarding/suggestions`. **Aucun endpoint ne permet au client de déclarer une étape terminée** — c'est ce qui rend la checklist digne de confiance.

## Module Opérations — Incidents · Automatisation · Gouvernance · Piste d'audit (branche `feature/operations-trustworthy`)
Chantier « rendre le module Opérations réel et digne de confiance ». Quatre lots, chacun avec sa migration, ses tests et ses commits atomiques (migrations `0048`→`0051`).

- **⭐ Piste d'audit exhaustive et infalsifiable** — trois changements. **(1) Chaînage par hachage** : chaque `AuditEvent` porte un `sequence` monotone par tenant, le `prev_hash` de l'entrée précédente et son propre `hash` SHA-256 couvrant tout son contenu (before/after inclus). `domain.VerifyAuditChain` est une **fonction pure** sur les lignes : le même verdict vaut sur la table live ou sur un fichier exporté. Modifier une entrée casse son hash ; la re-hacher casse le lien de la suivante ; en supprimer une laisse un trou. **(2) Une entrée par action** : le plugin GORM (qui sait *quelles lignes* ont changé) et le `Recorder` applicatif (qui sait *ce que l'action voulait dire*) écrivaient tous les deux. Pendant une requête HTTP ils déposent désormais leurs observations dans un `audittrail.Collector` de requête, et le middleware écrit **exactement une** entrée chaînée fusionnant le sens et la preuve avant→après. Hors requête (workers) le plugin écrit directement, chaîné. **(3) Exhaustif par construction** : `middleware.AuditMutations` monté sur le groupe `protected` journalise **tout POST/PUT/PATCH/DELETE réussi** — acteur, tenant, action, type+id de ressource, before, after, ip, user-agent, request_id, méthode, chemin, statut, horodatage. Une nouvelle route est couverte dès qu'elle est montée. Les appels refusés et les lectures ne sont **pas** journalisés (ils n'ont rien changé). **Rétention** configurable par tenant (0 = illimité, défaut ; minimum 30 j sinon) ; la purge **scelle** ce qu'elle retire (`AuditChainSeal` conserve le hash auquel la tête survivante se raccroche) donc la chaîne reste vérifiable de part et d'autre. **Export** CSV + JSON portant le verdict de chaîne **et** une signature HMAC-SHA256 (`AUDIT_EXPORT_KEY`) — sans clé le bloc signature **dit** pourquoi il est vide plutôt que de passer pour signé. Endpoints : `GET /governance/audit-events{,/verify,/export?format=}`, `GET|PUT /governance/audit-retention`, `POST /governance/audit-retention/apply`. Les deux destinations (`/audit-logs`, `settings/audit-log`) redirigeaient déjà vers `/governance/audit-trail` — une seule destination. **Preuve (test) : 20 actions distinctes de types différents à travers la vraie pile HTTP → exactement 20 entrées**, chacune complète, et la vérification de chaîne passe ; éditer une ligne stockée, en supprimer une et tronquer la tête sont chacun détectés et localisés. `AuditEvent` a perdu son défaut Postgres `gen_random_uuid()` pour que le **même schéma monte sous sqlite** — c'est ainsi que le DDL de ce test cesse de dériver du modèle (l'ancien DDL écrit à la main avait déjà dérivé).
- **Automatisation — tester sans déclencher.** L'ancien bouton « Tester » **exécutait** la règle pour de vrai. `POST /automation/rules/:id/dry-run` trace la règle contre un **enregistrement réel du tenant** (sévérités, CVSS, KEV, étiquettes d'actif les siennes) sans toucher **aucun** port d'action : verdict par étape (`would_run`/`would_skip`/`would_fail`/`not_reached`/`not_matched`), **payload tel qu'il entre dans chaque étape**, ce que l'étape produirait, et le **point d'échec** hissé en tête avec le payload à cet instant. Le contexte simulé avance comme en réel (l'étape 3 voit l'id de risque que l'étape 1 aurait créé). Un sujet **synthétique est annoncé comme tel** (un dry-run vert sur des données inventées ne doit jamais passer pour un dry-run vert sur les données du tenant). Overrides « et si c'était critique ? » sans toucher la prod. Traces enregistrées par id, **annulables en vol**, registre tenant-scoped dans les deux sens. Exécuter pour de vrai est un verbe séparé (`POST /rules/:id/run`, refuse sans `confirm:true`). **Cycle de vie** : `enable` / `suspend` avec **raison obligatoire** (une automatisation en pause sans explication est celle que le suivant réactive) ; `GET /automation/state` dérive la santé par règle (ok/degraded/failing/suspended/idle) + la phrase qui l'explique. **Historique** : mode (live/manual/replay), entrée, sortie, entrée+sortie+durée par étape, acteur, durée totale ; `POST /executions/:id/replay` rejoue avec l'entrée enregistrée et référence l'originale. **5 modèles** prêts à l'emploi, adoptés **suspendus** (un modèle qui se déclenche dès le clic est exactement la surprise qu'on supprime) ; `Describe(locale)` rend une règle en une phrase FR/EN. **Canaux** : ajout d'un webhook générique signé (HMAC-SHA256) et d'une passerelle SMS HTTP pilotée par noms de champs (aucun opérateur imposé) ; `POST /automation/channels/test` fait une **vraie livraison** par canal et rend l'erreur exacte. **Bug corrigé** : la condition « étiquettes d'actif » était un contrôle mort — rien ne peuplait jamais `AssetTags`, donc une règle ainsi filtrée (dont un des modèles) ne matchait jamais ; les étiquettes viennent maintenant des facettes structurelles de l'actif + des tags des risques qui lui sont liés, en live comme en dry-run.
- **Gouvernance — un workflow qui décide vraiment.** Les règles de décision vivent en **fonctions pures** (`domain/approval_engine.go`) : éligibilité, quorum, avancement, expiration — d'où « qui peut signer ? » côté UI et « celui-ci peut-il signer ? » côté API sans dérive. Approbateurs **nommés** et/ou par rôle. Chaînes **séquentielles** (défaut) ou **parallèles** (juridique/sécurité/finance signent sans s'attendre) ; un refus résout la demande entière dans les deux modes. **Quorum** en nombre ou en pourcentage des approbateurs nommés, borné au nombre de personnes qui pourraient le donner (un quorum supérieur à sa propre liste ne peut qu'expirer). Les **délégations** portent enfin les droits d'approbation (le verdict nomme les droits utilisés ; la décision enregistre qui a vraiment signé ; résolu côté serveur). **Expiration** : un worker clôt les demandes en retard en `expired` — état terminal distinct d'un refus ; l'échéance est **gelée à la soumission** comme les étapes. **Commentaire obligatoire au refus**, et ce commentaire voyage jusqu'au demandeur. **Notifications** (in-app + e-mail, best-effort) à qui peut signer maintenant — y compris qui couvre par délégation, sans quoi une délégation ne change rien. **Catalogue de types de demandes** remplaçant les paires entity/action en texte libre ; `risk_acceptance` reste épinglé par test sur `(risk_acceptance, accept)` parce que la garde `RESIDUAL_ACCEPTED` du cycle de vie en dépend. `GET /governance/approvals/:id` renvoie la progression par étape **et si l'appelant peut signer, avec la raison**. L'ancien `DecideApprovalStepUseCase` a été **supprimé**, pas laissé à côté de son remplaçant.
- **Incidents — provenance, liens réels, alertes, revue qui produit du travail.** **Provenance** : `origin` (manual/automation/scanner/cti/integration) + règle + exécution + preuve concrète → bandeau « Créé automatiquement par la règle X depuis la source Y » avec **lien vers la règle**, chip dans le registre, et page d'aide `/incidents/sources` listant les 5 sources avec les **compteurs réels du tenant** (une source jamais déclenchée affiche zéro). **Liens réels** : `RiskID *uint` face à des risques en UUID rendait incident→risque structurellement impossible ; `risk_ids`/`asset_ids` portent les vrais ids (l'ancienne colonne reste, inutilisée). **Notifications multi-canal** à la déclaration **et à chaque changement de gravité** (dans les deux sens — une baisse dit aux gens de se démobiliser), via **le même dispatcher** que l'automatisation (un second signifierait configurer Slack deux fois). **Post-mortem structuré** (chronologie, cause racine, facteurs aggravants, impact, détection, ce qui a bien marché, leçons, actions correctives) : publier le fige et transforme **chaque action corrective en vrai plan de mitigation** via le use case qu'utilise l'écran Mitigations ; ce qui n'a pas pu être converti est rendu avec la raison et **conservé**. **Obligatoire avant de clôturer un incident CRITIQUE** (uniquement critique : l'imposer partout produit des revues que personne n'écrit) ; le refus **nomme les champs restants**, et la garde échoue **fermée**.
